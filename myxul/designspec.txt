did one version utilise geronimo for inline byte code compilation

No, Jacl did not use Apache Geronimo. For inline bytecode compilation, Jacl (and later JTcl) utilized Janino, an embedded Java compiler.
The confusion likely stems from how these tools were deployed in enterprise architecture: IBM WebSphere Application Server—which historically heavily integrated Jacl for its administrative CLI scripting (wsadmin)—shares deep open-source roots, specifications, and libraries with Apache Geronimo.
Here is how the actual inline bytecode compilation engine worked in Jacl:
• The Compiler Component (TJC): Starting around Jacl 1.4.0, an extension called TJC (Tcl to Java Compiler) was introduced.
• The Inline Compilation Engine (Janino): When running in "runtime mode," a user could explicitly invoke a command like package require TJC followed by TJC::compile myProc. Instead of relying on a heavyweight external JDK or application server framework like Geronimo, TJC seamlessly generated Java source code from the Tcl procedure on the fly, and passed it directly to an ultra-lightweight embedded library named Janino.
• The Result: Janino compiled that code into raw Java bytecode entirely in memory, which was then immediately injected into the active Java Virtual Machine (JVM) interpreter thread to drastically accelerate execution speed.
Both Jacl and JTcl carried forward this design, keeping the inline compilation entirely dependent on Janino rather than any J2EE application server software.

In Jacl 1.4.1, you actually don't need to explicitly turn off runtime bytecode compilation because it is disabled by default.
Unlike native Tcl engines (which automatically compile code into bytecode in the background), Jacl is a pure interpreter. The TJC (Tcl to Java Compiler) engine and Janino will only compile a procedure if it is manually requested inside the script.
If you are dealing with a script or an environment where it is actively being triggered, there are two primary ways to disable or completely block it:

1. The Clean Way: Remove the Manual Activation Triggers

Because runtime compilation is entirely opt-in, it only happens if your script explicitly requests it. To stop it from happening, you just need to open the Tcl script and look for (and remove or comment out) the following lines:
tcl
# Remove or comment out these lines if you find them:
package require TJC
TJC::compile someProcName
Use code with caution.

2. The Absolute Way: Prevent it at the JVM/Classpath Level

If you are running a large, legacy enterprise application (such as older IBM WebSphere administrative scripts) and you cannot easily modify the underlying Tcl files, you can block Janino and TJC from loading entirely by adjusting the Java Classpath.
When Jacl starts up, it attempts to load dependencies from its library folder. If you remove the compiler components, Jacl will simply fall back to standard, safe interpretation:
1. Locate your Jacl installation directory or the lib/ext directory of your Java installation where Jacl's files reside.
2. Remove or rename the following two JAR files so the Java Virtual Machine cannot see them:
	• tjc.jar (The Tcl-to-Java compiler logic)
	• janino.jar (The embedded compiler engine)
Without those two JARs on the classpath, any accidental or hardcoded call to package require TJC will simply throw a standard, catchable Tcl error rather than consuming system memory and attempting to inject dynamically generated Java classes at runtime.

is jacl 1.3.3 codebase much smaller than jacl 1.4.1

Yes, the Jacl 1.3.3 codebase is significantly smaller than Jacl 1.4.1—both in terms of raw footprint and architectural complexity.
The differences span several areas:

1. Compiled Footprint (JAR File Sizes)

If you evaluate the binaries required to run the environment, Jacl 1.3.3 is roughly half the size of a full Jacl 1.4.1 deployment:
• Jacl 1.3.3: The core jacl.jar file is roughly 400 KB to 500 KB. It contains only the token parser, primitive Tcl command implementations, and basic Java reflection hooks.
• Jacl 1.4.1: The primary jacl.jar scales up to roughly 850 KB to 875 KB. However, if you include its auxiliary inline compiler extensions (tjc.jar and janino.jar), the complete execution footprint exceeds 1.5 MB.

2. Codebase and Structural Complexity

The physical lines of code and class files expanded drastically between these two versions due to major architectural overhauls:
• The Parser and Namespace Engines: Jacl 1.3.3 utilizes a very basic, linear string-parsing engine matching older Tcl 8.0–8.3 specifications. Jacl 1.4.1 completely replaced this with a far more complex, nested parser engine designed to support Tcl 8.4 namespaces, variable call-stack tracking (upvar), and execution traces.
• The Expression (expr) Engine: Jacl 1.3.3 evaluates math and logic expressions natively through basic Java parsing routines. Jacl 1.4.1 introduced a much heavier, strict type-checking mathematical evaluation engine to accurately emulate 64-bit integer overflows and Tcl 8.4's exact math rules.
• The Reflection Layer (TclBlend/Java Interop): Jacl 1.4.1 expanded the codebase further by including heavily updated reflection caching mechanisms. This was designed to prevent memory leaks when dynamically instantiating Java classes from inside Tcl, adding dozens of new internal tracking classes that do not exist in 1.3.3.

Summary

If you need a highly constrained, ultra-lightweight embedded script engine where memory footprint is a critical priority, Jacl 1.3.3 is much tighter. However, you trade away the enhanced performance optimizations, stability patches, and scoping/namespace safety features that account for Jacl 1.4.1's larger size.

No, nobody has ever ported Jim Tcl to Java.
Jim Tcl was specifically designed from scratch as an open-source, ultra-lightweight, pure C implementation (~14k lines of core code). Its entire purpose is to provide a small-footprint, embedded scripting engine for C/C++ applications or bare-metal embedded hardware.
Because the Java ecosystem already had Jacl and JTcl to serve the exact same niche (a small, embeddable Tcl interpreter) for the JVM, there was never a practical reason or community effort to port Jim Tcl's unique C architecture over to Java.

The Closest "Jim Tcl Alternative" in Java: Hecl

If you are looking for what Jim Tcl represents—a radically stripped-down, modernized, and lightweight "Tcl-like" language—but built natively for Java, you should look at Hecl.
• What it is: Hecl is a programming language written in Java that uses Tcl-style syntax (everything is a string, heavy use of commands and braces).
• The Philosophy: Just like Jim Tcl strips away the heavy baggage of core Tcl (like execution traces or complex Tk dependencies) to be lightweight on hardware, Hecl was written from scratch to be an ultra-small, fast Tcl variant specifically for memory-constrained Java environments (originally targeted at old cell phones running J2ME).
If you absolutely need a native JVM scripting language that follows strict Tcl syntax, stick with Jacl 1.3.3 for the lowest memory footprint, or JTcl for 8.4 syntax compliance.
