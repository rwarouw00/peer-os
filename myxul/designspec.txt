MYXUL DESIGN SPEC
A XUL application engine written from scratch in Java 8, JavaFX 8 and Nashorn

This is the cut-down context of an earlier design conversation, kept to one
direction: building our own XUL engine, in our own code and base classes, on
Java 8 only. Lines marked "Review:" correct or tighten what the conversation
originally said.


==============================================================================
1. GOAL AND CONSTRAINTS
==============================================================================

* Build desktop applications whose windows are described in Mozilla-style XUL
  markup, rendered by JavaFX, with their UI logic in JavaScript embedded in
  the XUL and run by Nashorn.
* Everything stays on Java 8. JavaFX 8 and Nashorn both ship inside Java 8,
  so the engine needs no scripting or UI libraries of its own.
  Review: Oracle JDK 8 includes JavaFX. Most OpenJDK 8 builds don't; use one
  that bundles OpenJFX 8 (for example Azul Zulu FX 8 or BellSoft Liberica
  "Full" JDK 8).
* All engine code is ours, written fresh in Java 8 style (generics, lambdas,
  java.util.function, try-with-resources). It is not a port of any older
  toolkit.
* Target desktop: Lubuntu. The engine is pure Java, so it also runs on
  Windows and macOS.


==============================================================================
2. WHY XUL, AND WHY NOT FXML
==============================================================================

FXML is open source too: it is part of OpenJFX, under the GPL v2 with the
Classpath Exception, the same licence as OpenJDK. Licensing is not the reason
to prefer XUL.

The reason is abstraction:

* FXML is a generic object serializer. <Button text="Click Me"/> makes Java
  reflect javafx.scene.control.Button and call setText("Click Me"). The markup
  mirrors JavaFX's class hierarchy, so FXML files are tied to JavaFX.
* XUL is a fixed, domain-specific vocabulary (<button>, <menu>, <tabbox>,
  <hbox>, <vbox>). It describes an application abstractly, and an engine maps
  each tag to a widget. The same XUL file could be rendered by JavaFX today
  and by another toolkit later without changing the markup.
* XUL keeps a clean separation: structure in XUL, style in CSS, UI logic in
  JavaScript, application and business logic in Java.
* Compared with GWT, which builds UIs imperatively in Java and transpiles to
  JavaScript, XUL is declarative and needs no compile step. Edit the file,
  reopen the window, and the change is there. XUL's box model (<hbox>,
  <vbox>, flex) also suits fluid desktop layouts better than GWT's
  table-based layouts.

Cost of this choice: unlike FXML, every XUL tag needs a handler in our engine
that maps it to a JavaFX node. That registry is the heart of the engine
(section 4).


==============================================================================
3. WHY JAVAFX AND NASHORN
==============================================================================

JavaFX 8 as the renderer:

* Its layout panes match XUL's box model closely: HBox for <hbox>, VBox for
  <vbox>, GridPane for <grid>, SplitPane for <splitter>, TabPane for
  <tabbox>, TreeView for <tree>, MenuBar/Menu/MenuItem for <menubar>/<menu>/
  <menuitem>, TextArea for <textbox multiline="true">.
* It has a scene graph, CSS styling of controls, observable properties and
  binding, and hardware-accelerated rendering.
* It runs the same on Windows, macOS and Linux.

Nashorn as the script engine:

* XUL handles UI events through attributes (oncommand, onclick, onkeypress,
  onfocus, onblur, onchange) whose values are JavaScript, and through
  <script> blocks. Without an embedded JavaScript engine those attributes are
  just dead strings. The embedded engine is not optional: it is how apps
  handle their UI events.
* Nashorn is built into Java 8 (javax.script, engine name "nashorn"), so
  there is nothing extra on the classpath, and it calls Java objects
  directly. A script can call methods on the JavaFX nodes the engine created,
  and on Java service objects the engine exposes.


==============================================================================
4. ENGINE ARCHITECTURE
==============================================================================

The whole engine fits in a small number of our own classes:

  XulParser         reads a .xul file (DOM via DocumentBuilder, or StAX) and
                    walks the element tree
  XulRegistry       maps each tag name to a builder that makes a JavaFX Node
                    from the element's attributes
  XulScriptManager  owns the Nashorn engine; loads <script> blocks; runs event
                    attribute code
  XulEventBus       wires event attributes on each node to the script manager
  XulDocument       the script-facing "document": getElementById() and the
                    element-to-node map

Flow:

  [ app.xul ] --> XulParser --> XulRegistry (tag -> Node builder) --> JavaFX scene graph
                      |                                                     |
                      +--> <script> blocks --> XulScriptManager (Nashorn) <-+
                                                ^          oncommand etc. via XulEventBus
                                                |
                                     document, window, Java services

4.1 Keep the toolkit behind an interface (optional but recommended)

To keep XUL independent of the renderer, the parser can talk to a factory
interface, with JavaFX as the first implementation:

  public interface XulWidgetFactory {
      Object createButton(Map<String, String> attributes);
      Object createVBox(Map<String, String> attributes);
      Object createLabel(Map<String, String> attributes);
  }

  public class JavaFXWidgetFactory implements XulWidgetFactory {

      @Override
      public Object createButton(Map<String, String> attributes) {
          Button button = new Button();
          if (attributes.containsKey("label")) {
              button.setText(attributes.get("label"));
          }
          if (attributes.containsKey("oncommand")) {
              String actionId = attributes.get("oncommand");
              button.setOnAction(e -> XulContext.execute(actionId));
          }
          return button;
      }

      @Override
      public Object createVBox(Map<String, String> attributes) {
          VBox vbox = new VBox();
          if (attributes.containsKey("spacing")) {
              vbox.setSpacing(Double.parseDouble(attributes.get("spacing")));
          }
          return vbox;
      }

      @Override
      public Object createLabel(Map<String, String> attributes) { ... }
  }

  // Bootstrapping
  XulEngine.setWidgetFactory(new JavaFXWidgetFactory());
  XulEngine.loadChrome("main_window.xul");

The same <button label="Save"/> could then become a JavaFX Button, or another
toolkit's button, without changing the XUL.

4.2 Parsing

  public void parseXul(InputStream in, Pane parentContainer) throws Exception {
      DocumentBuilderFactory dbf = DocumentBuilderFactory.newInstance();
      Document doc = dbf.newDocumentBuilder().parse(in);
      Element root = doc.getDocumentElement();
      buildUI(root, parentContainer);   // recurse through children, building the JavaFX graph
  }

Review: XUL files use the namespace
http://www.mozilla.org/keymaster/gatekeeper/there.is.only.xul. Call
dbf.setNamespaceAware(true) and match on local names. Also turn off external
entities (dbf.setFeature("http://apache.org/xml/features/disallow-doctype-decl",
true), or at least disable external general and parameter entities). That
stops a .xul file from pulling other local files into the UI.

4.3 The registry: tag name -> JavaFX builder

  public class XulRegistry {
      private final Map<String, Function<Map<String, String>, Node>> tagBuilders = new HashMap<>();

      public XulRegistry() {
          tagBuilders.put("vbox", attrs -> {
              VBox vbox = new VBox();
              if (attrs.containsKey("spacing")) vbox.setSpacing(Double.parseDouble(attrs.get("spacing")));
              return vbox;
          });

          tagBuilders.put("button", attrs -> {
              Button btn = new Button(attrs.getOrDefault("label", ""));
              if (attrs.containsKey("oncommand")) {
                  String jsFunction = attrs.get("oncommand");
                  btn.setOnAction(e -> scriptManager.invoke(jsFunction));
              }
              return btn;
          });
      }

      public Node createComponent(String tagName, Map<String, String> attributes) {
          return tagBuilders.getOrDefault(tagName, attrs -> null).apply(attributes);
      }
  }

Review: an unknown tag should not silently return null. Report it with the
file and line (or render a visible placeholder), so mistakes show up.

4.4 Layout: XUL flex on JavaFX

  if (attributes.containsKey("flex")) {
      VBox.setVgrow(childNode, Priority.ALWAYS);   // inside a <vbox>
      // HBox.setHgrow(childNode, Priority.ALWAYS) inside an <hbox>
  }

Review: Priority.ALWAYS makes a child take the spare room, but HBox and VBox
share it equally among growing children. They can't express proportional
flex (flex="1" next to flex="3"). For proportions, lay a box out with a
GridPane and percentage column or row constraints, or write a small custom
Pane (XulBox extends Pane, overriding layoutChildren()) that hands out spare
space by flex weight. The custom pane is a few dozen lines and also gives a
natural home for XUL's align and pack attributes.

Other XUL-to-JavaFX mappings to implement:

  <hbox>/<vbox>          HBox/VBox (or the custom XulBox)
  <grid>                 GridPane
  <splitter>             SplitPane (the splitter's neighbours become its items)
  <tabbox><tabs><tabpanels>  TabPane, pairing each <tab> with its <tabpanel>
  <tree>                 TreeView
  <listbox>              ListView
  <menubar>/<menu>/<menupopup>/<menuitem>/<menuseparator>
                         MenuBar/Menu/(the menu's items)/MenuItem/SeparatorMenuItem
  <toolbox>/<toolbar>/<toolbarbutton>  ToolBar and Buttons
  <statusbar>/<statusbarpanel>         an HBox of Labels
  <textbox>              TextField; <textbox multiline="true"> TextArea
  <label value="...">    Label
  <canvas>               javafx.scene.canvas.Canvas
  <separator>            Separator

Review: accesskey="N" has no direct JavaFX equivalent. JavaFX mnemonics come
from an underscore in the text (Menu "_File", MenuItem "_New") with
setMnemonicParsing(true), so the engine must insert the underscore before
the accesskey letter. Keyboard shortcuts (XUL <key>) map to
MenuItem.setAccelerator(KeyCombination.keyCombination("Shortcut+N")).

4.5 Threading

All JavaFX nodes must be created and changed on the JavaFX Application
Thread. Use Platform.runLater for work arriving from other threads; touching
live nodes from another thread throws IllegalStateException. Because event
handlers run on the FX thread, scripts run there too. A long script freezes
the window, so long-running work belongs in Java services on background
threads, posting results back with Platform.runLater.

4.6 Properties

JavaFX setters (setText, setDisable) cover XUL attributes. The JavaFX
properties behind them (textProperty(), disableProperty()) also allow
binding later, such as greying out a Save button while nothing has changed.


==============================================================================
5. SCRIPTING AND EVENTS (NASHORN)
==============================================================================

5.1 Embedded scripts in XUL

  <window id="MainWindow" title="My Application"
          xmlns="http://www.mozilla.org/keymaster/gatekeeper/there.is.only.xul">
      <script>
          function handleButtonClick() {
              alert("Button was clicked via JavaScript!");
          }
      </script>
      <button label="Click Me" oncommand="handleButtonClick()" />
  </window>

Review: Nashorn has no alert(). The engine has to provide it (and window,
document) as globals, for example alert() showing a JavaFX Alert.

5.2 The script manager

  public class XulScriptManager {
      private final ScriptEngine engine;

      public XulScriptManager() {
          ScriptEngineManager manager = new ScriptEngineManager();
          this.engine = manager.getEngineByName("nashorn");
      }

      public void evaluateInlineScript(String scriptContent) throws Exception {
          engine.eval(scriptContent);        // loads the <script> functions
      }
  }

  // Expose the document so scripts can find nodes
  engine.put("document", myXulDocumentTree);

  // In XUL JavaScript
  function updateUI() {
      var label = document.getElementById("theLabel");   // maps back to the JavaFX node
      label.setText("Updated via Javascript!");
  }

Calling a named function from Java:

  button.setOnAction(event -> {
      try {
          ((Invocable) engine).invokeFunction("handleButtonClick");
      } catch (Exception e) {
          e.printStackTrace();
      }
  });

5.3 XUL event attributes and the event object

oncommand is XUL's main action event. It fires on a click, on Space or Enter
while the control has focus, or on its access key. JavaFX's
setOnAction(EventHandler<ActionEvent>) has the same meaning, so oncommand
maps to setOnAction. onclick, onkeypress, onfocus, onblur and onchange map to
setOnMouseClicked, setOnKeyPressed, and focusedProperty() and
textProperty()/valueProperty() listeners.

In XUL, the attribute's code sees a variable named event. The original idea
was:

  <button id="submit-btn" label="Save Data" oncommand="validateAndSave(event)" />

  String jsCommand = attributes.get("oncommand");
  if (jsCommand != null) {
      javafxButton.setOnAction(fxEvent -> scriptManager.executeUiEvent(jsCommand, fxEvent));
  }

  public void executeUiEvent(String jsCode, ActionEvent fxEvent) {
      Bindings bindings = engine.createBindings();
      bindings.put("event", fxEvent);
      try {
          engine.eval(jsCode, bindings);
      } catch (ScriptException e) {
          e.printStackTrace();
      }
  }

Review (bug): engine.eval(code, bindings) with fresh bindings runs the code
against those bindings instead of the engine's own globals. The functions
defined by the <script> blocks (validateAndSave) and the globals document and
window are then not visible, and the call fails with "validateAndSave is not
defined". Instead, run the attribute's code as the body of a function that
receives event:

  // once per attribute, when the node is built
  ScriptObjectMirror handler = (ScriptObjectMirror) engine.eval(
          "(function (event) {\n" + jsCode + "\n})");
  javafxButton.setOnAction(fxEvent -> handler.call(null, fxEvent));

This keeps the window's globals, gives the code its event, compiles each
attribute once rather than per click, and reports syntax errors when the
window loads rather than at the first click. Report script errors to the
user (a dialog or notification, with the message and line) rather than
printing a stack trace.

  <script>
      function validateAndSave(event) {
          var targetButton = event.getTarget();     // the JavaFX Button
          targetButton.setText("Processing...");
          FileController.saveDoc();                 // a Java service exposed to scripts
      }
  </script>

5.4 One script context per window

Give each window its own ScriptContext (or its own engine), so two windows
of the same app don't share variables. Expose to each: document (that
window's XulDocument), window (title, close(), open dialogs), and the Java
services the app may use (such as file access), and nothing more.

5.5 Security note

Nashorn scripts can reach any Java class (Java.type("java.io.File"),
java.lang.Runtime). An app's scripts are fully trusted code. If apps ever
come from others, create the engine with a ClassFilter
(NashornScriptEngineFactory.getScriptEngine(ClassFilter), available from
Java 8u40) that allows only the classes the engine means to expose.


==============================================================================
6. ESTIMATED SIZE
==============================================================================

A from-scratch Java 8 engine should need fewer than 15 core classes, because:

* layout: JavaFX's HBox, VBox, GridPane and SplitPane already behave close to
  XUL, so the layout code is mostly attribute mapping (plus the small XulBox
  pane if proportional flex is wanted);
* events: lambdas and Nashorn turn each event attribute into one line of
  wiring, with no listener class per component;
* data: generics and Map<String, String> carry attributes without casting.

Review: treat "fewer than 15 classes" as a goal, not a measurement. The
widget list in 4.4, CSS translation and good error reporting are where the
lines will go.


==============================================================================
7. TESTING AGAINST REAL-WORLD XUL
==============================================================================

Use real XUL from established applications as a test corpus, in stages:

  Stage 1  Core layout: extract structural snippets (<vbox>, <hbox>, <button>,
           <toolbarbutton>, <label>) and check JavaFX sizes and stretches them
           as the original intended.
  Stage 2  Strip Mozilla specifics: flatten <overlay> files into one file;
           replace command="cmd_bold" style XPCOM hooks with plain JavaScript
           function calls.
  Stage 3  Events and scripts: run the original event attributes
           (oncommand="window.close();") through the Nashorn bridge.

  <hbox align="center" flex="1">
      <toolbarbutton id="bold-btn" label="Bold" tooltiptext="Bold Text"/>
      <toolbarbutton id="italic-btn" label="Italic" tooltiptext="Italic Text"/>
      <vbox flex="2">
          <label value="Font Size:"/>
      </vbox>
  </hbox>

Sources:

* SeaMonkey Composer: in a SeaMonkey build, the chrome/ folder's .jar files
  (ZIP archives, such as comm.jar or editor.jar) hold content/editor/
  editor.xul and its dialogs. The source is also downloadable, for example
  seamonkey-2.53.24.source.tar.xz.
* Komodo Edit (github.com/Komodo/KomodoEdit): src/chrome/ and src/content/,
  for example komodo.xul and the preferences dialogs. It's a strong stress
  test for <splitter> (SplitPane), <tabbox> (TabPane) and <tree> (TreeView).
  Its split between JavaScript in the UI and heavy logic in a backend
  matches our Nashorn-plus-Java-services design.
* Other XUL applications with distinctive layouts: Songbird/Nightingale
  (media library grids, sliders), Zotero's older XUL releases (three-pane
  collection tree, item list, detail pane), Google AdWords Editor before 2010
  (dense data forms), BlueGriffon and KompoZer (many dialogs, pickers),
  Celtx (custom document layouts). Wikipedia's "Software that uses XUL"
  category lists more.

8.1 Leafpad XUL (first target)

Leafpad was Lubuntu's minimal GTK+ 2 text editor in the LXDE era. It was
dropped when Lubuntu moved to LXQt in 18.10, partly because GTK+ 2 was
deprecated. A XUL rebuild needs only a handful of tags and doesn't depend on
the desktop's toolkit.

  <window id="leafpad-xul" title="Untitled - Leafpad XUL" width="640" height="480"
          xmlns="http://www.mozilla.org/keymaster/gatekeeper/there.is.only.xul">
      <menubar id="main-menubar">
          <menu label="File">
              <menupopup>
                  <menuitem label="New" accesskey="N" oncommand="EditorController.newFile()" />
                  <menuitem label="Open..." accesskey="O" oncommand="EditorController.openFile()" />
                  <menuitem label="Save" accesskey="S" oncommand="EditorController.saveFile()" />
                  <menuseparator />
                  <menuitem label="Exit" accesskey="Q" oncommand="window.close()" />
              </menupopup>
          </menu>
          <menu label="Edit">
              <menupopup>
                  <menuitem label="Cut" oncommand="document.getElementById('editor-textarea').cut()" />
                  <menuitem label="Copy" oncommand="document.getElementById('editor-textarea').copy()" />
                  <menuitem label="Paste" oncommand="document.getElementById('editor-textarea').paste()" />
                  <menuseparator />
                  <menuitem label="Delete" oncommand="document.getElementById('editor-textarea').clear()" />
              </menupopup>
          </menu>
      </menubar>
      <vbox flex="1">
          <textbox id="editor-textarea" multiline="true" flex="1" wrap="true"
                   style="font-family: monospace; font-size: 14px;" />
      </vbox>
  </window>

Tags needed: <menubar>/<menu>/<menupopup>/<menuitem>/<menuseparator>
(MenuBar, Menu, MenuItem, SeparatorMenuItem), <vbox flex> (VBox with
Priority.ALWAYS), <textbox multiline> (TextArea, with wrapping, scrollbars
and clipboard cut/copy/paste built in).

Review: "Delete" calling TextArea.clear() empties the whole document. To
delete the selection, call deleteText(getSelection()) or
replaceSelection(""). The xmlns in the original sample ("http://mozilla.org")
was wrong; it's corrected above.

  function openFile() {
      var filePath = NativeFileService.showOpenDialog();     // a JavaFX FileChooser, in Java
      if (filePath != null) {
          var content = NativeFileService.readFile(filePath);
          document.getElementById("editor-textarea").setText(content);
          window.setTitle(NativeFileService.getFileName(filePath) + " - Leafpad XUL");
      }
  }

8.2 AbiWord XUL (larger target)

AbiWord's document engine was separated from its user interface by its XAP
cross-platform layer. A XUL rebuild needs only the UI shell: toolbars, a
sidebar, a status bar and a central page view.

  <window id="abiword-xul" title="AbiWord XUL"
          xmlns="http://www.mozilla.org/keymaster/gatekeeper/there.is.only.xul">
      <toolbox>
          <toolbar id="main-toolbar">
              <toolbarbutton id="cmd-new" label="New" oncommand="FileController.newDoc()" />
              <toolbarbutton id="cmd-open" label="Open" oncommand="FileController.openDoc()" />
              <toolbarbutton id="cmd-save" label="Save" oncommand="FileController.saveDoc()" />
              <separator />
              <toolbarbutton id="cmd-bold" label="B" oncommand="FormatController.toggleBold()" />
              <toolbarbutton id="cmd-italic" label="I" oncommand="FormatController.toggleItalic()" />
          </toolbar>
      </toolbox>
      <hbox flex="1">
          <vbox flex="3" align="center" style="background-color: #808080; padding: 10px;">
              <canvas id="document-canvas" flex="1"
                      style="background-color: white; width: 816px; box-shadow: 2px 2px 5px rgba(0,0,0,0.3);" />
          </vbox>
          <vbox id="sidebar" flex="1" style="border-left: 1px solid #ccc;">
              <tabbox flex="1">
                  <tabs>
                      <tab label="Navigator" />
                      <tab label="Styles" />
                  </tabs>
                  <tabpanels flex="1">
                      <tabpanel><tree id="outline-tree" flex="1"/></tabpanel>
                      <tabpanel><listbox id="style-list" flex="1"/></tabpanel>
                  </tabpanels>
              </tabbox>
          </vbox>
      </hbox>
      <statusbar>
          <statusbarpanel id="status-page" label="Page 1 of 1" />
          <statusbarpanel id="status-mode" label="INS" />
      </statusbar>
  </window>

  function toggleBold() {
      var boldBtn = document.getElementById("cmd-bold");
      var isCurrentlyBold = boldBtn.getAttribute("checked") === "true";
      boldBtn.setAttribute("checked", !isCurrentlyBold);
      AbiCoreEngine.applyTextAttribute("font-weight", !isCurrentlyBold ? "bold" : "normal");
  }

<canvas> maps to javafx.scene.canvas.Canvas. The Java document model draws
pages with GraphicsContext.fillText() and friends.

Review:
* JavaFX CSS doesn't understand box-shadow, padding: 10px on a non-Region,
  or width on a Canvas. CSS properties need translating to JavaFX's -fx-
  ones (-fx-background-color, -fx-padding, -fx-effect: dropshadow(...)), and
  sizes to setPrefWidth or setWidth. The style translator is its own piece
  of work in the engine.
* getAttribute/setAttribute on a node assume XulDocument returns element
  wrappers that keep XUL attributes and map them onto the JavaFX node (here,
  checked onto a ToggleButton's selected state). Decide early whether
  scripts see raw JavaFX nodes or XUL element wrappers. Wrappers are more
  work but keep scripts toolkit-independent, which is the point of XUL.
* A real word processor needs editable rich text, not just a painted
  canvas: caret, selection, input methods. Leafpad first.


==============================================================================
9. BUILD ORDER
==============================================================================

1. XulParser + XulRegistry for <window>, <vbox>, <hbox>, <label>, <button>,
   <textbox>, with flex via Priority.ALWAYS; error reporting with file and
   line.
2. XulScriptManager: one Nashorn context per window; <script> blocks;
   document.getElementById; window.close/setTitle; alert.
3. Event wiring: oncommand -> setOnAction with an event parameter (5.3);
   then onclick, onkeypress, onchange, onfocus/onblur.
4. Menus (<menubar> ... <menuitem>, accesskey, <key>), then Leafpad XUL
   end to end, with a file service exposed to scripts.
5. Style translation (XUL/CSS -> JavaFX -fx- CSS) and the XulBox pane for
   proportional flex, align and pack.
6. <splitter>, <tabbox>, <tree>, <listbox>, <toolbar>, <statusbar>;
   test against Komodo and SeaMonkey Composer snippets.
7. AbiWord XUL shell.
